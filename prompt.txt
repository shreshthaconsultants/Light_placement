PROJECT CONTEXT
===============
I am building a ZWCAD lighting design tool for an MEP (Mechanical, Electrical, Plumbing) consulting company. The system has two parts:

1. ZWCAD .NET plugin written in C# (LightPlacementPlugin.cs)
   - Registers a command called "LIGHT" inside ZWCAD.
   - Prompts the user for: room type, fixture lumens, and a closed polyline boundary.
   - Extracts polyline vertices in millimeters from the ZWCAD drawing.
   - Sends HTTP requests to a local FastAPI backend.
   - Reads the JSON response and draws circles on a "LIGHTS" layer at each returned coordinate.
   - Shows a MessageBox with the calculation summary.
   - Uses the ZwSoft.ZwCAD.* namespaces (ApplicationServices, DatabaseServices, EditorInput, Geometry, Runtime, Colors).
   - Drawing units are assumed to be MILLIMETERS; coordinates are scaled to meters only when calling /calculate.

2. Python FastAPI backend (main.py, placement.py, config.py)
   - /calculate endpoint: takes room_type + polyline (in meters) + fixture_lumens, applies the lumen method (E × A) / (UF × MF), returns required number of lights.
   - /layout endpoint: takes polyline (in mm) + spacing constraints, runs a grid optimizer, returns light coordinates with grid metadata, bounding box, and notes.
   - Has thoughtful geometry helpers: shoelace area, point-in-polygon, point-to-segment distance, self-intersection detection, convexity check, centroid fallback for tiny rooms, wall clearance dropping.

THE CORE PROBLEM
================
The two endpoints are disconnected. /calculate says "you need 12 lights" based on photometric requirements. /layout independently generates a grid that might give 9 or 16 lights based on spacing constraints. The plugin shows both numbers in the MessageBox and tells the user "use a brighter/dimmer fixture to reconcile" — which is not a real solution.

Additionally:
- No photometric validation: after placing lights, we never check whether the actual lux distribution meets the target.
- No obstacle handling: real MEP ceilings have columns, beams, ducts, HVAC diffusers, and sprinklers. Lights must avoid these.
- Concave / L-shaped rooms only use bounding-box grids, which produces poor coverage.
- The plugin draws plain circles instead of real ZWCAD block references with attributes (wattage, lumens, mounting height, IES file reference).
- No way to specify mounting height or working plane height.
- No support for multiple fixture types in one room (e.g., downlights in circulation, panels in work areas).

UPGRADE 2 — Photometric validation
----------------------------------
Backend:
- After placing fixtures in /design (and as a standalone endpoint POST /validate), generate a validation grid of sample points inside the polygon at working plane height. Sample spacing default 500 mm, configurable.
- For each sample point, calculate illuminance from each fixture using inverse square law with cosine correction:
      E_i = (I × cos(θ)) / d²
  where:
      I = fixture_lumens / π    (Lambertian downlight approximation; configurable)
      θ = angle from fixture nadir to sample point
      d = 3D distance from fixture (at ceiling) to sample point (at working plane)
  Sum contributions from all fixtures for total lux at that sample point.
- Apply the room's maintenance factor (MF) and utilization factor (UF) from config.py to the final values.
- Return: avg_lux, min_lux, max_lux, uniformity_ratio (min/avg), meets_target (boolean — is avg_lux >= required_lux), and a warning flag if uniformity_ratio < 0.7 (IES standard for offices/classrooms).
- Add a new Pydantic model PhotometricResult and include it in the /design response.

Plugin:
- Display the photometric validation results in the MessageBox: avg/min/max lux, uniformity, and a clear pass/fail indicator.
- If uniformity < 0.7, color the MessageBox icon as Warning instead of Information.

UPGRADE 3 — Obstacle handling
